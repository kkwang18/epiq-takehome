# Decision Log

Format per the brief: `D-01`–`D-07` are the assignment's own required decisions; additional
IDs cover other significant decisions made along the way. A change to an existing decision gets
a new row referencing the old one, rather than editing history in place.

| ID | Decision | Why / trade-off | Date |
|------|----------|-----------------|------|
| D-00 | Language/runtime: Python 3.11+ | The problem is I/O-bound (HTTP calls to the stub, Postgres reads/writes), not CPU-bound, so Python's weaker raw throughput isn't a real cost here. Mature libraries for every piece we need (FastAPI, httpx, psycopg3) and OS-process workers are trivial via `subprocess.Popen`. Go would give a stronger single-binary "production" story but slower iteration for this scope; Node's multi-process/row-locking patterns are less idiomatic. | 2026-09-03 |
| D-01 | Work distribution: Postgres lease queue via `SELECT ... FOR UPDATE SKIP LOCKED`, no dedicated reaper process; lease renewed by a background thread while a worker holds an item, every write conditioned on `leased_by = $worker_id` | Each worker atomically claims a `pending` item or one whose lease has expired, in one statement: `UPDATE items SET state='in_progress', leased_by=$w, leased_until=now()+5s WHERE id = (SELECT id FROM items WHERE state='pending' OR (state='in_progress' AND leased_until < now()) ORDER BY created_at LIMIT 1 FOR UPDATE SKIP LOCKED) RETURNING *`. A killed worker's item becomes claimable purely because the next claim attempt's own `WHERE` clause already includes expired leases — no separate reaper loop, no supervisor, no shared memory. Processing one item can span multiple stub attempts with backoff (D-05), which can exceed a single lease window, so a background thread renews the lease every 2s (`UPDATE ... SET leased_until=now()+5s WHERE item_id=$1 AND leased_by=$2 AND state='in_progress'`) while work continues; a 0-row result means the lease was already stolen, and the thread flags the processing loop to abort. The actual safety guarantee isn't that flag, though — it's that *every* mutating statement touching this item (renewal, and the final terminal write) includes `leased_by = $worker_id`, so a stale worker whose lease has moved on can never resurrect it or clobber the new owner's result; a lost race simply updates zero rows. | 2026-09-03 |
| D-02 | Identity: `item_id` is a UUID per file path (never collapsed for duplicate bytes); a per-tenant `annotations_cache` keyed by `(tenant, sha256)` avoids redundant billed calls | Item identity and content identity are different things. Every file gets its own item row regardless of byte content, satisfying "duplicates never collapse into one item." Separately, `annotations_cache(tenant, sha256) -> annotation` lets an item whose content already has an annotation *for that tenant* skip the HTTP call entirely — turning the ~10% duplicate-content rate into avoided cost rather than merely-harmless repeat billing, while the cache key's `tenant` column makes cross-tenant leakage structurally impossible to read around. | 2026-09-03 |
| D-03 | Storage: single Postgres instance is the only durable store; no separate queue, cache, or blob store | At ≤500 items/run and 2 concurrent runs, a dedicated queue/cache technology is unjustified complexity. Postgres holds run/item state, extracted text (as `TEXT`), annotations (as `JSONB`), and doubles as the work queue via row leasing. The query surface (`item`/`items`/`status`) reads directly from these tables — no separate read path to keep in sync. | 2026-09-03 |
| D-04 | Terminal states: `succeeded`, `empty_content`, `decode_failed`, `annotation_failed`, `annotation_invalid_request`; every non-`succeeded` item carries a `reason JSONB` | The two pre-annotation edge cases get their own terminal states (matching the manifest's own `expected_outcome` names, since there's no reason to rename them). Retry-exhaustion on the stub (`annotation_failed`) is kept distinct from a `400` on our own request (`annotation_invalid_request`) because the latter indicates a bug in *our* request construction, not a flaky dependency — conflating them would misclassify a client defect as an external failure in review. `reason` carries the machine-readable detail (attempt count, last status, timestamps) ITEM-REQ-5 asks for. | 2026-09-03 |
| D-05 | Failure semantics at the stub boundary: 2s HTTP timeout; retryable = `500`, `429`, connection/timeout errors; non-retryable = `400` (terminal immediately); max 5 attempts; backoff `200ms × 2^(attempt-1)` capped at 2s, ±20% jitter | Cannot actually be deferred to M2 — M1 can't process a single item to completion without *some* policy here. Timeout sized against the stub's default fixed 150ms latency, leaving generous margin for capacity-gate queuing delay under contention. `429`/`500` are the dependency being flaky/at-capacity, not our fault, so worth retrying; `400` means our own request is malformed, and retrying changes nothing, so it terminates immediately as `annotation_invalid_request` rather than burning the retry budget. Jitter matters specifically because four workers contend for only 2 capacity slots (D-08) — synchronized retries would thrash the gate. Exhausting the retry budget on a retryable failure lands in `annotation_failed`. M2's fault harness will validate these values hold up under real concurrent load/failure; only that validation, not the policy itself, is deferred. | 2026-09-03 |
| D-06 | Secondary performance thresholds | **Deferred** to the M2 build, where thresholds (retry amplification, throughput degradation, completion time) can be set against real observed numbers instead of guessed in advance. Not silently skipped — recorded here as open. | 2026-09-03 |
| D-07 | Local-environment fidelity | **Deferred** alongside D-06 — written up once the M2 scenario is running and the real gaps (single-machine clock, no real network partition, etc.) are concretely known rather than speculated. | 2026-09-03 |
| D-08 | Capacity gate: `stub_call_slots` table (rows = configured `in_flight_capacity`), same lease-and-self-heal pattern as D-01, count sourced from config not hardcoded | Distinct from D-01 because item *ownership* and being *mid-HTTP-call* to the stub are different resources — a worker can own an item without currently calling the stub. A worker claims one of `in_flight_capacity` slot rows (short lease) before calling the stub and releases it in a `finally` right after; a SIGKILLed worker's slot self-heals the same way an item lease does. Rejected: Postgres advisory locks held for the call's duration — they release automatically on connection death, but only once the *server side* notices the TCP connection is gone, which without aggressively tuned keepalives can take far longer than our 10s recovery bound. A deterministic lease TTL is safer than relying on that timer. The slot count is read from the same `in_flight_capacity` config value used to start the stub (via `STUB_IN_FLIGHT_CAPACITY`), so the two can never drift apart. | 2026-09-03 |
| D-09 | `item_attempts`: one row per attempt, `INSERT` committed *before* the HTTP call is sent, `UPDATE` committed after it returns; `UNIQUE(item_id, attempt_no)` | Not a bare `attempt_count` counter, and not append-only despite an earlier draft calling it that (it is updated once, and is described as such here). The insert commits as its own transaction before the request goes out; the update commits as its own transaction after the response comes back. A worker SIGKILLed between the two leaves the row with `completed_at IS NULL` — durable, queryable proof an attempt was made and may have been billed, which is exactly what M2's reconciliation (REQ-2.2d) and `EVALUATION.md` need, rather than a derived guess a post-hoc counter could never produce. Note this is necessarily conservative in one direction: a row can exist with `completed_at IS NULL` even in the rare case the process died after the insert committed but before the HTTP request was actually sent — reconciliation should read such rows as "cannot rule out billing," not "billing confirmed." On claiming an abandoned item, a worker checks `item_attempts` for an already-completed successful attempt before reprocessing; if found, it finalizes the item from that record instead of re-calling the stub, closing one more window of duplicate billing (the harder case — crash strictly between billing and recording any outcome — remains genuinely unrecoverable, and is explicitly out of scope per the brief). `UNIQUE(item_id, attempt_no)` is a defense-in-depth backstop alongside the `leased_by` guards in D-01, in case a stale worker ever tries to insert using an attempt_no it computed before losing the lease. | 2026-09-03 |
| D-10 | Tenant provenance invariant: every worker read/write of `items` or `annotations_cache` uses `tenant` read from the `items` row the worker currently holds the lease on — never from any other source | Workers talk to Postgres directly and bypass the Pipeline API, so the API's tenant-scoping (REQ-1.2) does not reach them. This is the one place a worker could leak across tenants if it ever read `tenant` from worker launch config, a global, or anywhere other than the claimed row. Enforced by code convention plus an M1 test: two tenants submit corpora with byte-identical files, and the test asserts neither's cache entry or item write is ever touched by the other's processing, even under interleaved claims across workers. | 2026-09-03 |
| D-11 | Deployment: only Postgres runs in a container; the stub, Pipeline API, and workers run as native OS processes launched and tracked (PIDs) by `./intake up`/`down` | Corpus directories (`--out <dir>`) can be anywhere on the host filesystem, so containerizing the pipeline/workers would mean volume-mounting arbitrary host paths for no benefit. Native processes also keep localhost networking to the stub trivial. "Docker plus one language runtime" is read as: Docker for infrastructure (Postgres), the runtime for our own code. | 2026-09-03 |
| D-12 | Workers are separate OS processes from M1 onward, not in-process threads upgraded later for M2 | The brief's suggested build order allows in-process concurrency for M1, but the claim/lease SQL already has to be race-safe across unrelated processes — there is no simpler version of it for "just threads." Building the OS-process model once, correctly, and running it from day one avoids a second concurrency code path and de-risks REQ-1.4, which the brief itself flags as the requirement that determines whether M2 is achievable. M1 simply doesn't exercise `kill-worker` yet. | 2026-09-03 |
| D-13 | `corpus --verify` re-derives `seed`/`size`/`tenant` from the target directory's own `manifest.json`, not from re-typed CLI flags | Matches the brief's framing ("re-derives a corpus from its manifest's own arguments") — the user shouldn't need to remember or retype the original arguments to verify a corpus already on disk. Usage: `./intake corpus --verify --out <dir>`. | 2026-09-03 |
| D-14 | `submit` synchronously hashes every file and bulk-inserts all items in one Postgres transaction before returning `run_id` | At ≤500 small files, the scan is fast (sub-second), and atomicity is worth more than latency here: if the Pipeline API process dies mid-scan, no partial run/items exist to reconcile — the transaction simply never commits and the corpus can be resubmitted cleanly. An async background-ingest phase would need its own crash-recovery story for a phase that's already fast at this scale. REQ-1.3's "queryable while the run is still processing" refers to annotation/extraction progress, not this initial ingest step. | 2026-09-03 |
