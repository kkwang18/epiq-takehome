# Decision Log

Format per the brief: `D-01`–`D-07` are the assignment's own required decisions; additional
IDs cover other significant decisions made along the way. A change to an existing decision gets
a new row referencing the old one, rather than editing history in place.

| ID | Decision | Why / trade-off | Date |
|------|----------|-----------------|------|
| D-00 | Language/runtime: Python 3.11+ | The problem is I/O-bound (HTTP calls to the stub, Postgres reads/writes), not CPU-bound, so Python's weaker raw throughput isn't a real cost here. Mature libraries for every piece we need (FastAPI, httpx, psycopg3) and OS-process workers are trivial via `subprocess.Popen`. Also it's a language I am very familiar with. | 2026-09-03 |
| D-01 | Work distribution: Postgres items table doubles as the work queue. Workers claim rows with FOR UPDATE SKIP LOCKED and hold them via a leased_until timestamp, renewed every 2s by a background thread while processing. No reaper: an expired lease is reclaimed by the next ordinary claim query. Every item write is conditioned on leased_by = $worker_id. Progress is reported by aggregating per-state counts for ./intake status. | Items are independent, so any completion order is valid and SKIP LOCKED can hand out rows freely. Recovery falls out of the claim query itself rather than needing a reaper, supervisor, or heartbeat, and the leased_by predicate on every write is what makes it safe: a stalled worker that lost its lease updates zero rows instead of clobbering the new owner. Trade-off: Postgres-as-queue buys transactional consistency between work assignment and item state at the cost of throughput, since polling and renewal writes grow with worker count. Batched claims, then LISTEN/NOTIFY, then partitioning would carry this well before a dedicated queue service earns the dual-write problem it introduces. | 2026-09-03 |
| D-02 | Identity: `item_id` is a UUID per file path (never collapsed for duplicate bytes); a per-tenant `annotations_cache` keyed by `(tenant, sha256)` avoids redundant billed calls | Item identity and content identity are different things. Every file gets its own item row regardless of byte content, satisfying "duplicates never collapse into one item." Separately, `annotations_cache(tenant, sha256) -> annotation` lets an item whose content already has an annotation *for that tenant* skip the HTTP call entirely — turning the ~10% duplicate-content rate into avoided cost rather than merely-harmless repeat billing, while the cache key's `tenant` column makes cross-tenant leakage structurally impossible to read around. Trade-off: dedup is best-effort, not guaranteed — the cache is only written on success, so a duplicate claimed while the original is still retrying misses and calls independently, meaning billed calls will exceed unique-content count by a small margin rather than matching it exactly.| 2026-09-03 |
| D-03 | Storage: single Postgres instance is the only durable store; no separate queue, cache, or blob store | One store means work assignment and item state change in the same transaction, so there is no window where a claim succeeded and the state write didn't. Splitting the queue out buys throughput at the cost of that atomicity, and against a billed dependency with no idempotency key, a lost state write means paying twice with nothing recorded — the failure mode this pipeline can least afford. That reasoning doesn't weaken at scale; Postgres-as-queue runs well past this volume, and what changes is tuning rather than the choice. Trade-off: claim and renewal writes contend with query reads on one table, and extracted text sits in the row the claim query scans — addressed incrementally (separate content from work-tracking columns, materialize per-state counters, move text to blob storage) before a second system is warranted. | 2026-09-03 |
| D-04 | State model: `pending`, `in_progress` (nonterminal); `succeeded`, `empty_content`, `decode_failed`, `processing_error`, `annotation_failed`, `annotation_invalid_request` (terminal). A backing-off item is `pending` with `next_attempt_after` set (D-05). Every non-`succeeded` item carries `reason JSONB` shaped `{"code": <enumerable>, ...detail}`; `annotation_failed` also carries `last_outcome`. Retryable means a later attempt could plausibly differ; non-retryable means it provably cannot — stub-specific codes and limits in D-05. | empty_content, decode_failed, processing_error, and annotation_invalid_request are all deterministic properties of the bytes, the environment, or our own request, so they terminate on first detection rather than burning a retry. annotation_invalid_request separates a bug in our request construction from a flaky dependency, and last_outcome (malformed_response, unexpected_status) separates retries exhausted against a conformant dependency from retries exhausted against one violating its contract. Contract violations stay on the retryable path rather than failing fast, so a stub returning garbage burns the full retry budget before terminating — chosen because the alternative risks terminating a recoverable item on one bad response. And the worker's catch-all still retries unexpected exceptions (a transient Postgres error, say) indefinitely via lease self-heal, deliberately: giving every conceivable exception its own terminal state would blur "permanent, detected condition" with "transient infrastructure hiccup."| 2026-09-04 |
| D-05 | Failure semantics at the stub boundary: 2s HTTP timeout; retryable = `500`, `429`, connection/timeout errors; non-retryable = `400` (terminal immediately as `annotation_invalid_request`); max 5 attempts, enforced at claim time by counting `item_attempts` rows; backoff `200ms × 2^(attempt-1)` capped at 2s with ±20% jitter, applied by releasing the item (`state='pending'`, lease cleared, `next_attempt_after=now()+backoff`) rather than sleeping in-process. Retry exhaustion lands in `annotation_failed`. | The 2s timeout sits against a fixed 150ms latency plus loopback, so it fires only when the stub is wedged; tightening it would risk burning a retry, and a billed call, on ordinary variance. The 5-attempt cap is chosen against the stub's 1-in-7 schedule: treating failures as ~independent, a cap of 3 predicts ~2.4 spuriously failed items per run while 5 predicts ~0.05, so 5 is where the dependency's normal behavior stops producing terminal failures and a nonzero `annotation_failed` count means something is actually wrong. Enforcing that cap durably rather than in a per-invocation loop matters because a worker dying mid-sequence lets the next claimant restart at `attempt=1` — the effective cap would be per-invocation, and an item could accumulate more than 5 real billed attempts across its lifetime. Releasing the item for backoff rather than sleeping means a backing-off item holds neither a lease nor a capacity slot, so a retrying item doesn't take a worker out of circulation under M2's two-tenant load; jitter accordingly desynchronizes *when items become reclaimable*, so a burst of failures doesn't stampede the 2-slot gate at once. **Trade-off:** a released item costs an extra claim cycle per retry and can be picked up by any worker, so attempt state must live entirely in `item_attempts` rather than in worker memory. | 2026-09-04 |
| D-06 | One threshold added, on retry amplification: total attempts ≤ `ceil(X × 1.1666 × 1.5)`, where `X` is items that actually reach the stub (originals only, from each manifest) and `1.1666 = (1-p⁵)/(1-p)` is expected attempts per item at `p = 1/7` under D-05's cap; +5 for the fault execution's killed item. No thresholds on throughput or completion time — wall-clock, items/sec, and the billed-call delta are measurements only. Additive to the mandatory assertions: can fail an execution that would otherwise pass, never the reverse. | Both inputs are fixed before any run, so the bound is a prediction rather than a line drawn around observed results. It catches what would inflate attempts beyond policy: a cap not enforced durably, or leases stolen from live workers. The other metrics get no bar because nothing independently predicts wall-clock on arbitrary hardware, and a bar on the billed-call delta would relocate REQ-2.4's headline number into a fake secondary gate. **Trade-off:** the 1.5× margin absorbs variance and best-effort cache dedup, so this catches systemic breakage, not occasional. | 2026-09-04 |
| D-07 | Local-environment fidelity. **Real:** the stub's latency, failure schedule, capacity cap, and billing all happen over the network stack; `kill-worker` sends a real `SIGKILL` to a real OS process. **Simulated or untested:** single machine, so no real network partition (only a localhost socket disappearing), no multi-host clock skew affecting lease timing, no disk or OS-level fault injection (unreadable files are constructed deliberately), and Postgres as a single container rather than a replicated topology. | Written against what the harness actually exercises, not speculated in advance. The gaps bear directly on M2's claims: the 10-second recovery bound is proven only under single-machine clock conditions, and D-09's billed-but-unrecorded window is demonstrated by `SIGKILL` on a local process rather than a network-level disconnect from Postgres, which could show different timing. | 2026-09-04 |
| D-08 | Capacity gate: `stub_call_slots` table, one row per configured `in_flight_capacity`, claimed with the same lease-and-self-heal pattern as D-01 and released in a `finally`. Row count read from the same config value that starts the stub. | Item *ownership* and being *mid-HTTP-call* are different resources — a worker can hold an item without calling the stub — so the gate is separate from D-01's lease. A SIGKILLed worker's slot self-heals exactly as its item lease does. Rejected: advisory locks held for the call's duration, which release on connection death but only once the server notices the TCP connection is gone; without tuned keepalives that can exceed the 10s recovery bound, and a deterministic lease TTL is safer than relying on that timer. | 2026-09-03 |
| D-09 | `item_attempts`: one row per attempt, `INSERT` committed before the HTTP call is sent and `UPDATE` committed after it returns, with `UNIQUE(item_id, attempt_no)`. On claiming an abandoned item, a worker first checks for an already-completed successful attempt and finalizes from that record rather than re-calling. | A worker SIGKILLed between the two commits leaves a row with `completed_at IS NULL` — durable, queryable proof an attempt was made and may have been billed, which is what REQ-2.2's reconciliation needs and a post-hoc counter could never produce. Conservative in one direction: such a row can also mean the process died after the insert but before the request went out, so reconciliation reads it as "cannot rule out billing," not "billed." Checking for a completed attempt on reclaim closes one duplicate-billing window; the harder case, a crash strictly between billing and recording any outcome, is genuinely unrecoverable and out of scope per the brief. `UNIQUE(item_id, attempt_no)` backstops D-01's `leased_by` guards against a stale worker inserting with a stale attempt number. | 2026-09-03 |
| D-10 | Tenant provenance: every worker read or write of `items` or `annotations_cache` takes `tenant` from the `items` row it currently holds the lease on, never from launch config, a global, or any other source. | Workers reach Postgres directly and bypass the Pipeline API, so the API's tenant scoping (REQ-1.2) does not cover them — this is the one place a worker could leak across tenants. Enforced by convention plus an M1 test: two tenants submit byte-identical corpora and the test asserts neither's cache entry or item write is touched by the other's processing under interleaved claims. | 2026-09-03 |
| D-11 | Deployment: only Postgres runs in a container; the stub, Pipeline API, and workers run as native OS processes, launched and PID-tracked by `./intake up`/`down`. | Corpus directories can be anywhere on the host, so containerizing the pipeline would mean volume-mounting arbitrary host paths for no benefit, and native processes keep localhost networking to the stub trivial. Reads "Docker plus one language runtime" as Docker for infrastructure, the runtime for our own code. | 2026-09-03 |
| D-12 | Workers are separate OS processes from M1 onward, not in-process threads upgraded for M2. | The claim/lease SQL has to be race-safe across unrelated processes regardless, so there is no simpler version of it for threads. Building it once and running it as real processes from day one avoids a second concurrency code path and de-risks REQ-1.4, which the brief flags as the requirement determining whether M2 is achievable. M1 simply doesn't exercise `kill-worker` yet. | 2026-09-03 |
| D-13 | `corpus --verify` re-derives `seed`/`size`/`tenant` from the target directory's own `manifest.json` rather than re-typed flags. Usage: `./intake corpus --verify --out <dir>`. | Matches the brief's framing of re-deriving a corpus from its manifest's own arguments; the user shouldn't have to remember the original arguments to verify a corpus already on disk. Treats `--seed`/`--size`/`--tenant` as conditionally required, since they are mandatory in the fixed CLI table but meaningless under `--verify`. | 2026-09-03 |
| D-14 | `submit` synchronously hashes every file and bulk-inserts all items in one transaction before returning `run_id`. | At ≤500 small files the scan is sub-second, and atomicity is worth more than latency: if the API dies mid-scan the transaction never commits, so there is no partial run to reconcile and the corpus can simply be resubmitted. An async ingest phase would need its own crash-recovery story for something already fast at this scale. Reads REQ-1.3's "queryable while the run is still processing" as referring to annotation and extraction progress, not this ingest step. | 2026-09-03 |
| D-15 | Cross-run claim fairness: claim query orders by `order_index, created_at` rather than `created_at, order_index`. | `created_at` is the transaction timestamp, so every item in one run shares a value and the second run submitted would sort entirely behind the first — tenant-b's items wouldn't be claimed until tenant-a had nearly drained, making REQ-2.3's concurrent processing impossible. Since `order_index` restarts at 0 per run, sorting on it first interleaves runs at fine grain. Within a single run this is behaviorally identical, since `created_at` was constant and `order_index` was already the sole differentiator, so D-02's intra-run cache benefit (originals claimed before duplicates) is unaffected. | 2026-09-04 |
